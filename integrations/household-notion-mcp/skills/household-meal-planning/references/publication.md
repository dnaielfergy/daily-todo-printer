# Reviewed private GitHub publication

Read this only for private snapshot preparation or review. Use the authenticated GitHub connector and the user-configured **private** print inbox. Re-read current `main` `inbox.json`, any existing weekly manifest, and current `policies/household.md`, validating the repository, ref and file provenance. Fail closed on policy/source access failure. Keep all real meals/snapshots out of the public repository.

1. Show the **complete** intended lunch/dinner week, explicit omitted slots/cancellations, recipe components, effective servings, leftovers, and full categorized grocery list (or explicit no-groceries decision). Breakfast is not a v1 printable recipe job. User must explicitly approve the exact week, complete menu, individual servings, grocery quantities and grocery inclusion. A generic request to plan or save Notion is not approval.
2. For preview or review, create a private review branch, never write to `main`. Each dated lunch/dinner slot has one immutable recipe job with `schema_version:1`, distinct safe `job_id`, `date`, `meal`, and 1–12 independently scaled `recipes` with title, servings, ingredients and steps. See parent repo `docs/recipe-jobs.md` for the canonical schema.
3. Approved grocery data, if included, is one immutable grocery job with matching `week_start` and `plan_revision`; 1–12 categorized groups, max 120 total items. See parent `docs/grocery-jobs.md`. Keep recipe ingredients intact even when grocery policy omits some shopping entries.
4. Weekly `weeks/<Monday>/manifest.json` contains a complete list of current meal job paths, optional grocery path, and increasing revision. Root `inbox.json` indexes at most eight active manifests, retaining unrelated weeks. Changed snapshots use new globally unique IDs/files; never mutate historical job payloads. Whole-week withdrawal needs a higher-revision empty-jobs manifest with no grocery, not index deletion.
5. Validate JSON/refs/paths/IDs, dates, max 14 meals/week, distinct date+meal, matching grocery revision, same pinned private commit, maximum sizes and CP437-safe printer text. Create a **review PR** clearly labeled unapproved; preview its actual complete diff and itemized contents. **Do not merge** or activate `inbox.json` until the user separately explicitly approves that exact reviewed publication. Revalidate PR and `main` after approval before merge.
6. A merge makes data available to Windows importer, **not** physical printing. `recipe sync --preview` is read-only validation; `recipe sync` imports to SQLite without printing; only separately authorized local `recipe print` / `grocery print` emits paper. Do not execute any Windows import/print as part of normal planning. Fail safe on any partial/error state.

For staged QA use synthetic jobs and an isolated database; test negative authorization, invalid policy, stale revision, and repeat import. Never use live meals or production inbox for fixture testing.
